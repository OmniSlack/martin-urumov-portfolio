Ported to `<RUN_DIR>/t4-port/shade.py` as `seq_step(v, max_)`, plus the `SEQ` list.

**Does it behave the same as the original? Yes, on everything I tested, but only because I added special handling. A direct line-for-line port would not match.**

The trap is a negative `v` (with positive `max`). In JS, `Math.floor(v/max*6)` goes negative, `Math.min(5, negative)` stays negative, and `SEQ[-1]` is `undefined`. A naive Python port gives `SEQ[-1]`, which wraps around to `"f"`, the top shade. So for example `seqStep(-1, 10)` is `undefined` in JS and `"f"` in the naive port. My port returns `None` in these cases to match JS's `undefined`.

The port also handles two other differences:
- **NaN:** a NaN ratio (for example `inf/inf`, or a NaN input) gives `undefined` in JS. The port returns `None`.
- **Infinity:** `+inf` clamps to `"f"` and `-inf` gives `None`, as in JS. Inputs are converted with `float()`, so huge integers can't raise an overflow error that JS wouldn't.

`max <= 0` returns `"a"`, same as JS. If `max` is NaN, that check is false and the result is `None`, same as JS.

**Test:** I ran the JS and Python versions side by side on 3,400 inputs and compared the results. The inputs were a grid of edge values (0, -0, negatives, tiny and huge numbers, ±Infinity, NaN) crossed with each other, plus 3,000 random values from -0.5 to 1.5 times max. There were 0 mismatches.

**Caveats:**
- `undefined` has no Python equivalent, so I used `None`. A caller that treats the result as a string must handle `None`.
- I only tested numeric inputs. JS would coerce strings, `null` and similar values silently. The port does not mimic that, and `float()` on non-numeric input will raise.
