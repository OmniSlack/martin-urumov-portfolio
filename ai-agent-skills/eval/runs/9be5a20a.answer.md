I wrote the port to `<RUN_DIR>/t4-port/shade.py`. It has `seq_step(v, max_)`, plus a `seqStep` alias and the `SEQ` list.

**It behaves the same as the original for numeric inputs, but only because I added handling for the places where a plain translation would differ.**

I ran both versions on 25,026 `(v, max)` pairs and got 0 mismatches. The pairs were:
- 26 hand-picked cases: boundaries, negatives, zero or negative `max`, NaN, ±Infinity, and float-rounding cases such as 0.1+0.2 against 0.3.
- 20,000 random floats, including negative values and negative `max`.
- 5,000 random integer pairs.

Where a literal port would have differed:
- **Negative `v`:** `v/max*6` can be below 0, so the index is negative. JS gives `undefined` for `SEQ[-1]`, but Python would silently return `"f"` (the last element). The port returns `None` instead.
- **NaN:** `v` or `max` can be NaN, or `Infinity/Infinity` can occur. JS gives `undefined`. Python's `math.floor(nan)` raises `ValueError`. The port returns `None`.
- **Infinity:** `math.floor(inf)` raises `OverflowError` in Python. The port clamps positive infinity to `"f"` and returns `None` for negative infinity, as JS does.
- **Division:** JS never raises on division. The `max <= 0` guard in both versions prevents division by zero. I guard the `Infinity/Infinity` case explicitly.

Limits of the check:
- The port returns `None` where JS returns `undefined`. They are not the same object, but they mean the same thing. A caller that checks `=== undefined` needs to check `is None`.
- I only tested numeric inputs. JS would coerce strings, `null` and booleans, which this port does not copy. It calls `float()` on both arguments, so a non-numeric string raises an error, whereas JS gives NaN and then `undefined`.
- Around 5,000 of the 25,026 cases returned `undefined`/`None`, so those paths were well exercised.
