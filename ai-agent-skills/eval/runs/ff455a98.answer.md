Port written to `t4-port/shade.py` (`seq_step(v, max_)`). Verdict: on everything I tried it behaves the same as the JS original, with the caveats below. I have not proven equivalence.

**Porting traps (handled on purpose)**
- JS `SEQ[-1]` is `undefined`. Python `SEQ[-1]` wraps around to `"f"`. A plain translation would silently differ for every negative `v`. The port returns `None` for a negative index, which stands in for JS `undefined`.
- Python `math.floor(nan)` and `math.floor(inf)` raise. The port handles NaN and Infinity explicitly.
- The `Math.min(SEQ.length - 1, ...)` clamp is kept. It is what makes `v == max` return `"f"` instead of running past the end of the array.

**Defect in the original (not in the port)**
`seqStep` has no guard for negative values or NaN. `seqStep(-1, 10)` returns `undefined` in JS. The port reproduces this as `None` rather than "fixing" it. Whether that should be fixed is your call.

**COVERED INPUT SPACE**
Both implementations were run on identical inputs and compared exactly with `==`. No tolerance was used.
- 264 hand-picked grid cases: 22 values × 12 maxes.
  - Values: 0, 1, 2, 3, 5, 9.999999, 10, 10.0001, 11, 20, -1, -0.0001, -10, -100, 0.5, 1e-9, 1e308, ±Infinity, NaN, and two values near bucket boundaries.
  - Maxes: 10, 1, 6, 0, -1, -5, 0.1, 3, Infinity, NaN, 1e308, 5e-324.
- 10,000 pseudo-random samples: max in [0, 100), v in [-15, 115).
- 1,325 exhaustive integer cases: every k in 0..m for m = 1..50. These hit every exact bucket boundary and `v == max`.
- 11,589 cases in total. 1,202 of them return `undefined` in JS (negatives, NaN, and similar), and the port matched all of those too.
- Result: 0 mismatches.

**EDGES SEARCHED ON PURPOSE**
- `v == max` (the clamp case).
- `max <= 0`.
- Negative `v`.
- NaN and ±Infinity for both arguments.
- Subnormal and huge magnitudes.
- Exact bucket boundaries.

**NOT COVERED**
- Non-numeric inputs: strings, booleans, null, undefined, and so on. JS coerces them and Python would raise or behave differently. The port is only defined for numbers.
- Python integers above 2^1024, which can't convert to float. JS numbers are always doubles.
- Rounding behaviour in the last digit of `(v / max) * 6`. Python floats are IEEE doubles, the same as JS, and the exhaustive boundary cases agreed. I did not prove this for all doubles.
- `-0`: only incidentally covered.
- Hidden state and side effects: the function is a pure function with no state, so these should not apply. I confirmed this only by reading it, not by running it repeatedly.

**Bottom line:** the port matches on all 11,589 inputs tried, including the edges above. That is "matched on what I tried", not a proof, and the NOT COVERED list is where it could still differ.
