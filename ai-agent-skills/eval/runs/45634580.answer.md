I ported `seqStep` to `t4-port/shade.py` as `seq_step`, with `seqStep` as an alias. For every input I tried, it behaves the same as the original, but only because I handled several places where a literal translation does not.

**Where a literal port differs**
- **Negative values:** for `v < 0` with `max > 0`, JS computes a negative index. `SEQ[-1]` is `undefined` in JS, but in Python `SEQ[-1]` wraps around to `"f"`. For example, `seqStep(-1, 10)` is `undefined` in JS, and a literal port would return `"f"`.
- **NaN and Infinity:** `math.floor` raises on NaN and infinity, while JS carries them through to `undefined` or `"f"`.
- **Division by zero:** Python would raise on it. It never happens here, because `max <= 0` returns `"a"` first.

**What the port does**
It returns `None` wherever JS returns `undefined`. Those cases are negative-index results, `v` or `max` being NaN, and `-Infinity`. Where JS returns `"f"`, so does the port, including when the quotient is `+Infinity`. `max <= 0` returns `"a"` in both. One thing I did not preserve: the port converts its arguments with `float()`, so it assumes numeric input. JS type coercion of strings or `null` is not reproduced.

**How I checked**
I ran the original under `node` and the port under `python3` on the same 105,625 `(v, max)` pairs. They included negatives, zero, `-0`, NaN, ±Infinity, ±1e308, a subnormal, and exact bucket boundaries. They also included 300 random values between -20 and 20, crossed with each other. There were 0 mismatches. A naive port, with no special handling, mismatched on 26,604 of those pairs, so the comparison does detect the differences.

**Limit:** this is a test over sampled inputs, not a proof. The only tested floating-point boundaries were fractions like 1/3 and 2/3. `v / max * 6` has the same operation order in both languages and both use IEEE doubles, so I expect them to agree, but I have not tested every input.
