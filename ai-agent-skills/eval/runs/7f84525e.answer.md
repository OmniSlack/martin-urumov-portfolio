**Short answer: the port matches the original on everything I tried, but I have not proven it identical.** Where the two languages would have differed, I wrote the port to follow JavaScript's behaviour deliberately.

Port: `t4-port/shade.py`, function `seq_step(v, max_)`.

**Where a straight port would have been wrong**
- **Negative index.** `v < 0` with `max > 0` gives a negative index. JS `SEQ[-1]` is `undefined`, but Python `SEQ[-1]` is `"f"` (it wraps around). A naive port silently returns the top shade for negative values. My port returns `None`, matching JS `undefined`.
- **NaN and infinity.** JS `Math.floor(NaN)` gives NaN and then `undefined`, and `v / 0` gives `Infinity`. Python raises on `math.floor(nan)` and `math.floor(inf)`, and on division by zero. The port handles these explicitly.
- **Clamp at `v == max`.** `min(5, ...)` is kept, so `v == max` gives `"f"` and not an out-of-range index.

**Defect in the original, not in the port.** A negative `v` is not guarded: `seqStep(-1, 10)` returns `undefined`. I copied that behaviour instead of fixing it. If you want a guard (for example clamp to `SEQ[0]`), that is a change to the original as well.

**COVERED INPUT SPACE**
10,580 inputs, run through `node` for the original and `python3` for the port, with `cmp.js` and `cmp.py` in `t4-port/`:
- 10,000 pseudo-random pairs, with `max` in 0 to 100 and `v` in -10 to 110.
- 230 pairs hitting the bucket boundaries exactly: `max` 1 to 50 and `v = max*k/6` for k = 0 to 6.
- A hand-picked grid of 23 `v` values by 10 `max` values (230 pairs). The `v` values include negatives, 0, `max`, just above `max`, NaN, ±Infinity, 1e308 and 5e-324. The `max` values include -1, 0, NaN, Infinity and 1e308.

**KNOWN MISMATCHES**
None found. 0 of 10,580.

**EDGES SEARCHED ON PURPOSE**
`v == max`, `v < 0`, `max <= 0`, NaN, ±Infinity, float extremes and exact bucket boundaries. All of them matched.

**NOT COVERED**
- Non-numeric inputs: strings, `null`, `undefined`, booleans, BigInt. JS coerces these, Python does not, and the port does not imitate that.
- Signed zero (`-0`) was not specifically checked.
- Rounding differences exactly on a boundary for values other than `max*k/6` for integer `max` 1 to 50 and k 0 to 6. Both languages use IEEE-754 doubles, so I expect agreement, but that is inference, not measurement.
- The output type differs by design: JS `undefined` becomes Python `None`. This is not a behavioural match in the strict sense.

The port matches the original on 10,580 tested inputs, but that is a measurement of those inputs only. I know what the function does, but not what the shades are for, because the colours are placeholder letters.
